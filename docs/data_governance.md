# Data Governance Policy for Omega V5

This document outlines the data governance framework for the Omega V5 arbitrage engine. It establishes policies for data ownership, quality, security, and lifecycle management to ensure the integrity, reliability, and compliance of the system.

## 1. Data Ownership and Stewardship

- **On-Chain Data (Pools, Tokens):** The `config.py` `PROTOCOL_REGISTRY` and `ASSET_MATRIX` are the canonical sources of truth for supported assets and protocols. The core development team is the steward for this data. Changes must be validated against on-chain contracts.
- **Runtime Data (Opportunities, Prices):** This data is ephemeral and generated by the discovery and ranking engines. It is owned by the `omega-engine` process. Its integrity is governed by the `pipeline_validation.py` and `invariant_math.py` modules.
- **Cached Data (Redis):** The Redis cache (`redis_cache.py`) is for performance acceleration of non-critical metadata (e.g., RPC health, token properties). Data is owned by the producing process and must have a TTL. It is not a source of truth for execution.
- **Persistent State (SQLite Indexer):** The `indexer_state.py` SQLite database stores discovered pool states and events to accelerate boot-up. It is owned by the indexer/discovery process. Data is considered stale if it exceeds `INDEXER_STATE_MAX_AGE_BLOCKS`.
- **Benchmark & Audit Data (`out/`):** All operational outputs, logs, and reports are owned by the script that generated them (e.g., `run_full_benchmark_and_readiness.ps1`). These are critical for audits and performance analysis.

## 2. Data Quality and Integrity Standards

- **Schema Enforcement:** All data passed between major components (e.g., from discovery to ranking) must conform to the `unified_invariant_route_schema.md`.
- **Automated Validation:** The `pipeline_validation.py` script serves as a critical gate, running checks like `validate_payload_ids_and_sequence` to ensure economic invariants and protocol ID alignment before any opportunity is staged.
- **Data Integrity Gate:** The `run_full_benchmark_and_readiness.ps1` script includes a "Data Integrity" check that verifies the health of the SQLite indexer and Redis cache, contributing to the final readiness score.

## 3. Data Lifecycle Management

- **Creation:** Data is created by discovery services (scanners, API clients) or generated by internal processes (ranking, simulation). All data creation events should be logged with timestamps.
- **Storage:**
  - **In-Memory:** For active, real-time opportunity data.
  - **Redis:** For short-lived, non-critical metadata with a strict TTL (`REDIS_RPC_CACHE_TTL_SECONDS`).
  - **SQLite:** For semi-persistent, boot-up acceleration data with a max block age (`INDEXER_STATE_MAX_AGE_BLOCKS`).
  - **File System (`out/`):** For long-term audit trails, benchmark results, and PnL reports.
- **Archival & Deletion:**
  - The `scripts/ops/manage_data_backups.ps1` script is used to archive the `out/` directory.
  - The `indexer_state.py` module includes a `prune_all_stale_data` function to remove old records from the SQLite database.
  - Redis keys expire automatically via TTL.

## 4. Backup, Recovery, and Monitoring

- **Backup:** Regular, automated backups of the `out/` directory and the SQLite indexer DB are managed by `scripts/ops/manage_data_backups.ps1`. Redis persistence (AOF/RDB) can be configured for disaster recovery.
- **Recovery (DR):** In case of catastrophic failure, the recovery process is:
  1. Provision a new secure VM using `provision_secure_vm.sh`.
  2. Restore the latest backup of the `out/` directory.
  3. Run the `cloud_run_finalizer.ps1` script. The system will rebuild its state from on-chain data and the restored indexer.
- **Monitoring:** The `run_full_benchmark_and_readiness.ps1` script and the `/health` API endpoint provide continuous monitoring of data components.

## 5. Security and Access Control

- **Encryption:**
  - **In Transit:** All external communication must use encrypted channels (HTTPS, WSS, `rediss://`). This is enforced through configuration in `.env` and `config.py`.
  - **At Rest:** Private keys and secrets are stored in GCP Secret Manager, not on disk. The `provision_secure_vm.sh` script automates this.
- **Access Control:**
  - The production VM is hardened with firewall rules allowing SSH only via Google's IAP.
  - The application uses a dedicated IAM service account with least-privilege permissions.
  - The `.env` file is used to manage environment-specific configuration without hard-coding secrets in the source code.

## 6. Training and Continuous Improvement

- **Training:** All developers and operators must be familiar with this governance policy and the security guidelines in `.xgrok/SECURITY.md`.
- **Review Process:** Benchmark results from `docs/backtesting_guide.md` are used to review performance and identify data-related bottlenecks. These reviews inform the continuous improvement cycle.
- **Change Management:** All changes to data models, schemas, or governance policies must be documented in commit messages and, if significant, in this document.

## 7. Compliance and Auditing

- **Internal Audits:** The `audit_omega_v5.ps1` script provides a baseline for security and structural audits. The "Data Integrity Gate" in the readiness script provides a continuous, automated audit of data components.
- **External Compliance:** While DeFi is rapidly evolving, the system is designed with transparency and verifiability in mind. All executed trades are recorded on-chain and auditable via the `Accountant` module, which logs to a persistent database.
- **Reporting:** Stakeholders can review system performance and profitability through the data stored in the `out/` directory and the live dashboard.
